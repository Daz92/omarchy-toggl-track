space and e are different doors. One shows you what the machine recorded. The other changes what will be written to Toggl. Mixing them was the mistake in the current panel, where the only expansion drops you straight into a text field.

Rows no longer collapse each other. toggleBlock() currently closes every sibling, so comparing two blocks means clicking four times. Any number of drawers can stay open.

Apply stays explicit. A guessed row carries ~ until you touch it. ⇧↵ applies only rows that are ready, never guesses you have not confirmed.

One request at a time. request() returns early when requestPending is set, so batch apply drains applyQueue one row at a time. The row in flight says so; the panel does not freeze.

The stack encodes proportion, not category. A 4 px band split by project time — enough to see "that was a support week" without a legend. Untracked-but-recorded time shows as a neutral segment, so a day that is half unassigned looks half unassigned.

Two flags, not a badge cloud. ◌ means the day has ActivityWatch blocks nobody applied. ▲ means a conflict is sitting there. Everything else is silent.

Week totals get their own column. Cheap to compute, and the number people actually check.

Ranges differ in kind, not scale. At a week a day gets 68 px of width and 156 px of height, so it can carry a real time axis and you can see that Thursday was six fragments and a conflict. At a fortnight that collapses to a 9 px density strip. At a month, to a 4 px stack. Each is the most the space honestly supports.

Toggl will not answer past 4 June, and this is measured, not assumed. The API refuses any start_date earlier than 91 days ago, so the ‹ stops there. Paging further cannot show an empty grid — it must not offer the move at all. Full evidence in D5 below.

Theme coordination audit

5 FINDINGS measured against the built-in shell plugins

The shell exposes surface-scoped colour roles — Color.popups.*, Color.menu.*, Color.tooltip.* — and every built-in popup uses them. A panel is a popup surface. This plugin paints one with bar colours and hand-computed dimming.

What a theme can and cannot reach

Every Qt.darker() tier is a value the theme author has no way to influence. Twenty-one of them, across every muted label, every meta line, and every disabled state in the panel.

The fix is not a new palette. It is using the roles the shell already publishes.

IDFINDINGWHEREFIX
T1 Panel paints with bar.foreground and Color.background, so a theme's [popups] block is ignored entirely. Panel.qml:16, throughout Take Color.popups.background / .text / .border.
T2 Panel overrides the one component that was themed correctly — it passes foreground: root.foreground; background: Color.background into every SearchableDropdown, replacing that component's own Color.popups.* defaults. Panel.qml — 5 dropdowns Drop both overrides. The component is already right.
T3 21 hand-rolled dim tiers via Qt.darker(). No theme token behind any of them, and the 1.5 / 1.6 / 1.8 factors are used inconsistently for the same semantic role. Panel.qml, 21 sites Three named panel properties built with Util.alpha(Color.popups.text, …), so tiers track whatever the theme sets.
T4 Row hover and selection are hand-drawn instead of Style.hoverFill / Style.selectedFill, which already carry the theme's [controls] alphas. Panel.qml — recent list, day rows Use the Style fills. Free hover, focus and selected states.
T5 popups.background-alpha supports translucency; hard-coding Color.background forces the panel opaque while other popups follow the theme. Panel.qml Use the composed role and inherit the alpha.
Visible consequence, shown above. Color.popups.border falls back to Color.accent, so a coordinated panel is bordered in #89b4fa under aether, matching every other popup in the shell. Every panel on this page is drawn with that border — that is the change, not a styling choice I made.

Backend audit

The helper handles exactly one JSON request per process and exits. Nothing here proposes a daemon — every fix below works inside that constraint.

Where the sluggishness is

IDFINDINGWHERECOST
P1 Opening the panel fires bootstrap, then sync from its response — two cold Python starts, each spawning secret-tool as a subprocess before any HTTP happens. Panel.qml:onCompleted → handleResponse 2× startup before first paint
P2 /me/time_entries is refetched on every sync over the whole window, even when the metadata cache is fresh. The since parameter — documented, delta by modification time — is unused. toggl_api.py:1096, 1138 dominant call at 365d

Logging

NEW in the install dir · 24-hour ring · titles never written at default level

So a bug report has something to attach, and so the performance claims in §07 get verified rather than believed. One JSON object per line — greppable, tailable, parseable without a reader.

Where

<plugin dir>/logs/toggl.jsonl
os.path.dirname(os.path.abspath(__file__))
normally ~/.config/omarchy/plugins/daz.toggl-track/
Two consequences of logging into the install directory, both accepted. Your install is a symlink into the git working tree, so logs/ must join .gitignore in the same change or every write dirties the repo. And omarchy plugin remove deletes the logs with the plugin — correct for a log that belongs to the install.

Logging never raises into the request path. A read-only install or a permissions failure disables it silently for that process and the request proceeds.

A record

{"ts":"2026-09-04T09:14:22.108Z","lvl":"info",
 "action":"sync","ms":412,"ok":true,
 "http":[{"path":"/me/time_entries",
         "status":200,"ms":244,"bytes":48210}],
 "cache":{"workspace":"fresh","entries":"miss"},
 "counts":{"entries":114,"projects":37}}

Levels

LEVELEMITS
offnothing; the file is not created
errorsfailures only
infodefault — one record per action: timings, HTTP statuses, cache states, counts
debugadds ActivityWatch bucket ids, per-block segmentation timings, and the classifier prompt and response

Redaction, enforced at the writer

  • The API token is never written, at any level, on any path. Covered by a test over the log writer.
  • Window titles, topic names, entry descriptions and project names are not written at info. Counts and durations are.
  • debug does write them, and the settings control says so plainly.
  • Every string field truncates at 500 characters.
Why redaction is not optional here. The entire reason classification runs locally is that window titles do not leave the machine. A verbose log sitting in the install directory would quietly undo that.

Ring buffer — age first, size second

older than 24h · dropped
kept
new
  • Appends are a single write() on O_APPEND. No lock on the common path.
  • Crossing 1 MiB takes an exclusive flock, rewrites keeping only the last 24 hours, releases.
  • Still over after that, the oldest survivors drop until it fits. Age is the bound; size is the backstop.
  • Pruning runs at most once per process, after the record is appended, so it never delays a response.
  • A malformed line is dropped during a prune, never aborts it.

Panel-side events ride along. Panel.qml writes no files. A dropped request or a queue overflow accumulates in a bounded array of 32 and travels on the next request as client_log, flushed with "src":"qml". No extra process.

09

Build and install

NEW nothing to package — Omarchy installs plugins from git

omarchy plugin add <git-url> clones into a staging directory, validates the manifest, and moves it to ~/.config/omarchy/plugins/<manifest.id>/. There is no archive format to invent and no installer to write for the normal path. What the repo lacks is a release gate and a local install path.

build — a gate, not a compiler

Nothing compiles; QML and Python ship as source. It exits non-zero on the first failure and says which.

#CHECK
1omarchy plugin validate . — passes today, exit 0
2py_compile the helper and its tests
3unittest discover -s tests
4node tests/test_model.mjs
5bash -n setup build install
6qmlformat over Panel.qml and every ui/*.qml, by exit status, never piped
7BarWidget.qml skipped and listed as hand-review — both tools reject function open(): void, which IpcHandler requires
8tree clean; manifest.json version not already tagged
9nothing that must not ship is tracked — no logs/, no *.gguf, no __pycache__/, no token anywhere
10dist/…tar.gz + SHA256SUMS for offline install and release attachments
Step 6 is the one that has already bitten this repo. qmllint writes nothing on failure, so qmllint x.qml | tail returns tail's exit status and a broken file reads as green. This produced a false "baseline passes" during development. Check the status directly.

install

install                  # copy into ~/.config/omarchy/plugins/
install --dev            # symlink instead, edit in place
install --enable         # also: omarchy plugin enable … center
install --uninstall      # remove, keep token + cache + logs
install --uninstall --purge # also remove secret, cache, model
  • Target directory comes from manifest.json's id, never hard-coded, so a rename cannot orphan an install.
  • Refuses to overwrite a non-symlink install without --force, and names what is there.
  • --dev reproduces the symlink you placed by hand — the existing setup keeps working and stops being undocumented.
  • It does not run setup. Token entry and the model download stay explicit.
The one manual step it prints. omarchy-restart-shell. A reloadConfig keeps the plugin's Loader alive so a panel edit never appears, and rescanPlugins is not in this shell's IPC surface at all — it prints nothing and exits 0, indistinguishable from success. It must not be suggested.

Repository, for sharing

  • README.md leads with omarchy plugin add <git-url> --enable.
  • .gitignore gains logs/, dist/, *.gguf.
  • manifest.json carries the new settings and their defaults, so a fresh clone starts valid.
  • The model is never committed. 378 MB, fetched by setup.
  • setup becomes idempotent — an existing token is kept unless --reset, an existing model is checksum-verified rather than refetched.
